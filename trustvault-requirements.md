# TrustVault — Requirements

Scope and constraints are in `trustvault-project.md` and are not repeated here. Every requirement
below has an ID; tasks in `phases/` reference these IDs instead of restating the requirement.

Reference vault for benchmarks: **1 000 items, 4 fields each**, generated by
`trustvault-core`'s `benchfixture` helper. All timings measured on the development machine
(Ubuntu 26.04, x86-64) unless stated, and re-measured on each platform at G-C.

## Functional requirements

Priority: `must` blocks release, `should` is dropped only with a decision log entry, `could` is a
stretch goal.

| ID | Requirement | Priority | Accepted when | Phase |
|----|-------------|----------|---------------|-------|
| R-01 | The vault core shall serialize and deserialize all seven item types without loss | must | Property test round-trips 10 000 generated vaults byte-identically | 1 |
| R-02 | The `.tvault` header shall carry the format version and the Argon2id parameters (m, t, p, salt) in plaintext, authenticated as AEAD associated data | must | Editing any header byte causes decryption to fail, not to silently use different params | 1 |
| R-03 | A wrong master password shall be indistinguishable from a corrupted file | must | Both paths return the same error type and take the same time (±5 %) | 1 |
| R-04 | Any single flipped byte in the file shall cause a decrypt failure, never a partial or garbage read | must | Mutation test flips each byte of a small vault; all fail closed | 1 |
| R-05 | Saving shall be atomic — write to a temp file in the same directory, fsync, then rename | must | Killing the process mid-save leaves the previous vault intact and openable, over 100 injected kills | 1 |
| R-06 | Every AEAD nonce shall be drawn from the OS CSPRNG, never from a counter | must | Code review + `grep` gate in CI; documented in `docs/vault-format.md` | 1 |
| R-07 | The recovery kit shall unwrap the master key without the master password, and shall be shown exactly once at creation | must | Create vault → record kit → unlock with kit only | 1, 2 |
| R-08 | Onboarding shall create a vault in three steps: name & location, master password, recovery kit | must | All three screens match the design and produce a readable `.tvault` | 2 |

Declared once, here, at Phase 1. Declaring late means reworking what was already built to a looser
rule.

| Track | Declaration | Consequence |
|-------|-------------|-------------|
| Hardware | not applicable | — |
| Firmware | not applicable | — |
| Software | **Tier 2 overall, Tier 1 for `trustvault-core`** | vault: `90-MOC/Software Development Standard.md`. The core carries the higher tier because a defect there is unrecoverable data loss: known-answer vectors, mutation testing, ≥ 90 % coverage, and `forbid(unsafe_code)`. The UI carries Tier 2: typed, linted, smoke-tested, not exhaustively unit-tested |
| Compliance | none | No radio, no EMC, no safety certification. Code signing is a distribution requirement, not compliance |

## Interface contract

The boundary is not hardware ↔ software but **`trustvault-core` (plaintext) ↔ webview (untrusted)**,
because the prior-art survey established that the webview's heap cannot be wiped
(`tauri-apps/tauri` discussion #10852). The contract is therefore a security boundary:

- The core owns every plaintext byte. It exposes Tauri commands, never raw state.
- No command returns more than **one** secret value per invocation (R-10).
- Item lists cross the boundary with secrets **elided** — masked placeholders and metadata only.
- `reveal_field(item_id, field_id)` returns one value and starts a 10 s server-side timer; when it
  expires the core pushes a `field-remasked` event and the frontend drops its copy.
- `copy_field(item_id, field_id)` never returns the value at all — the core writes it to the
  clipboard itself and schedules the clear. The secret does not enter JS.
- On lock, the core zeroizes and emits `vault-locked`; the frontend clears its stores on receipt but
  is **not trusted** to have done so — every subsequent command re-checks the lock state.
- Behaviour when the link drops: the webview crashing or reloading does not unlock anything. The
  core's lock state is authoritative and survives a frontend reload.
- Behaviour on power loss mid-write: R-05 atomic save. The previous vault is always the fallback.

## Open questions

- [ ] **Import from other password managers** — which formats, if any, ship in v1? R-29 cannot be
      written as a testable requirement until this is answered. Blocks the **Phase 3 gate**.
- [ ] **Audit log retention** — R-13 says reveals are logged; nothing says for how long, or whether
      the log is inside the encrypted vault or beside it. A plaintext log of *which* secrets were
      revealed and when is itself sensitive. Blocks the **Phase 2 gate**.
- [ ] **Argon2id default parameters** — S-03 fixes the target (≥ 500 ms) but the m/t/p triple that
      hits it must be measured, not guessed, and it differs per platform. Blocks the **Phase 1 gate**.
