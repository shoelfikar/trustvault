# TrustVault — Requirements

Scope and constraints are in `trustvault-project.md` and are not repeated here. Every requirement
below has an ID; tasks in `phases/` reference these IDs instead of restating the requirement.

Reference vault for benchmarks: **1 000 items, 4 fields each**, generated by
`trustvault-core`'s `benchfixture` helper. All timings measured on the development machine
(Ubuntu 26.04, x86-64) unless stated, and re-measured on each platform at G-C.

The helper builds it in memory, which is all a `cargo bench` needs and is not all the criteria
need: S-02 and S-04 are about the **running application**, so the same vault has to exist as a
file something can open. That is what the example writes, in about two seconds:

```sh
cargo run --release --example reference-vault -p trustvault-core \
    --features benchfixture -- /tmp/reference.tvault
```

Its master password is a published constant and it prints it. The vault is a fixture and is not
to be used for anything else; the `benchfixture` feature is off in the shipped library precisely
so the application can never produce one.

**S-07 was one criterion until 2026-08-15** — *"Watchtower full scan, reference vault, ≤ 10 s incl.
HIBP, in-app timer, warm network"* — and it is split rather than relaxed, **D-77**. It is recorded
here rather than deleted because the original is the thing later readers will want to argue with.
Measured against the live service the day the contract was written, one range request takes 0.53 s
(1.87 req/s on a reused connection; 2.5 req/s at concurrency 8, so the limit is not the handshake).
The reference vault holds 1 000 **distinct** passwords, so a full check is 1 000 requests ≈ **400 s**
— 40× the criterion, and ten seconds buys about 25 passwords. Meeting it as written needs 100
sustained requests per second aimed at a free service. The wall-clock half survives as S-07a, where
it measures this code; the network half becomes S-07b, which states what this code can be held to,
because a stopwatch on the network half measures the user's link and HIBP's cache.

**S-07a's target was deliberately blank until it had been measured once** — filled 2026-08-15,
**D-80**, the day the first reading was taken. Naming a number before that would have been inventing
a value to fill a heading, and the caveat recorded with the first measurement is what the fixture is:
`benchfixture.rs` gives every item the password `pw-{index}-xK9`, so the reference vault has **no
reuse to group and effectively one zxcvbn score**. That is fine for a timing floor and wrong for a
typical one — dictionary matching is where zxcvbn spends its time, and this fixture gives it nothing
to match. The number set from it is the **cheap** case, and R-23 and R-24 have a fixture of their own
rather than this one: `auditfixture.rs`, twenty-one items with reuse groups of known size and a
password at every score.

**Where the 8× between 61 ms and 500 ms goes**, because a budget whose slack is unaccounted for is a
budget nobody can argue with later. **×1.9** is the cheap case made expensive: the same benchmark
scans the audit vault at 0.118 ms per password against the reference vault's 0.061 ms, so a vault of
passwords zxcvbn's dictionaries actually match costs about twice as much per item. **×2** is the
allowance every measured criterion here carries for a machine that is not this desktop. What remains
is headroom to the point at which a command that returns reads as a hang: the local scan reports no
progress and cannot — `watchtower-progress` exists for the breach half only (`docs/ipc-contract.md`
§8) — so half a second is the line, and it is the same order as S-03's deliberate 511 ms unlock. The
scan is never what makes opening a vault feel slow.

Two things follow that are worth writing down rather than rediscovering. The budget is **per 1 000
items**, not per vault: at 0.12 ms a password on the expensive side, a 10 000-item vault is over the
line and needs the progress events the breach half already has. And the ten weak findings in the
reference vault are a **property of the fixture**, not a defect — anything asserting that a scan of
it is clean is asserting something false.

## Functional requirements

Priority: `must` blocks release, `should` is dropped only with a decision log entry, `could` is a
stretch goal.

| ID | Requirement | Priority | Accepted when | Phase |
|----|-------------|----------|---------------|-------|
| R-01 | The vault core shall serialize and deserialize all seven item types without loss | must | Property test round-trips 10 000 generated vaults byte-identically | 1 |
| R-02 | The `.tvault` header shall carry the format version and the Argon2id parameters (m, t, p, salt) in plaintext, authenticated as AEAD associated data | must | Editing any header byte causes decryption to fail, not to silently use different params | 1 |
| R-03 | A wrong master password shall be indistinguishable from a corrupted file | must | Both paths return the same error type and take the same time (±5 %) | 1 |
| R-04 | Any single flipped byte in the file shall cause a decrypt failure, never a partial or garbage read | must | Mutation test flips each byte of a small vault; all fail closed | 1 |
| R-05 | Saving shall be atomic — write to a temp file in the same directory, fsync, then rename | must | Killing the process mid-save leaves the previous vault intact and openable, over 100 injected kills | 1 |
| R-06 | Every AEAD nonce shall be drawn from the OS CSPRNG, never from a counter | must | Code review + `grep` gate in CI; documented in `docs/vault-format.md` | 1 |
| R-07 | The recovery kit shall unwrap the master key without the master password, and shall be shown exactly once at creation | must | Create vault → record kit → unlock with kit only | 1, 2 |
| R-08 | Onboarding shall create a vault in three steps: name & location, master password, recovery kit | must | All three screens match the design and produce a readable `.tvault` | 2 |
| R-09 | The app shall lock on demand, on auto-lock timeout, and on OS sleep/lock | must | Each of the three triggers zeroizes the key and shows the lock screen | 2 |
| R-10 | Decrypted secrets shall cross the IPC boundary one field at a time, only on explicit user action | must | No IPC command returns more than one secret value; enforced by `src-tauri/tests/ipc_audit.rs` — **not** a core test, because N-02 forbids `trustvault-core` from depending on Tauri, so the core cannot see a command at all (D-39) | 2 |
| R-11 | The item list shall render the reference vault without visible lag while scrolling | must | 60 fps sustained, measured with the frame timeline | 2 |
| R-12 | Secret fields shall mask by default, reveal for at most 10 s, and re-mask on navigation | must | Reveal, wait 11 s, field is masked; navigate away and back, masked | 2 |
| R-13 | Every reveal shall append an entry to a local audit log when the setting is on | must | Log file contains one entry per reveal with timestamp and item id, and no secret value | 2 |
| R-14 | Copying a secret shall clear the clipboard after the configured interval | must | S-11 passes on all three platforms | 2 |
| R-15 | The generator shall produce passwords from the four toggleable character classes at lengths 8–64 | must | Every combination produces a password using exactly the selected classes | 3 |
| R-16 | ⌘K shall fuzzy-search item titles, usernames, URLs, and tags, and expose actions | must | S-04 met; Enter copies the password, ⇧Enter opens the item, Esc closes | 3 |
| R-17 | Items shall be creatable, editable, and deletable for all seven types | must | Each type round-trips through the Add dialog into the vault and back | 3 |
| R-18 | Deleting an item shall require a dialog naming the item; deleting a vault shall require typing the vault name | must | Neither destructive action can complete without the confirmation | 3 |
| R-19 | Every list shall have an empty state with an icon, one sentence, and one primary action | must | No reachable blank pane exists | 3 |
| R-20 | TOTP codes shall be generated per RFC 6238 (SHA-1, 6 digits, 30 s) with a visible countdown | must | Codes match a reference implementation for the RFC test vectors | 3 |
| R-21 | Settings shall expose UI scale, launch at login, auto-lock, clipboard clear, reveal logging, and theme, and shall persist them | must | Each setting survives a restart and takes effect without one | 3 |
| R-22 | Multiple vaults shall be openable, switchable, and independently locked | must | Switching vaults locks the outgoing one and zeroizes its key | 3 |
| R-23 | Watchtower shall detect reused passwords across the open vault | must | Three items sharing a password are all reported | 4 |
| R-24 | Watchtower shall score strength with zxcvbn and show a crack-time estimate in words | must | Estimates match zxcvbn's own output for a fixture set | 4 |
| R-25 | Breach checking shall use the HIBP range API with k-anonymity and `Add-Padding: true` | must | Two claims, one capture. **What leaves**: only a 5-character SHA-1 prefix — no full hash, no password, no item title, no vault or item identifier. **What returns**: the padded response carries **at least one zero-count row** and is **larger than the unpadded response for the same prefix**. The criterion read "responses are 800–1000 rows" until 2026-08-15 and that band is impossible rather than unmet — prefix `21BD1` returns **1 924 real rows** before any padding, twice the ceiling, and HIBP does not control that number. The decoy count is not fixed either: **110, then 125, then 156** for the same prefix inside one day, with the 1 924 real suffixes byte-identical every time. | R-26 | Breach checking shall be opt-in and off by default | must | S-10 passes on a fresh install | 4 |
| R-27 | Window size and pane widths shall persist across launches | should | Resize, quit, relaunch — geometry restored | 3 |
| R-28 | The app shall follow the OS theme by default, with a manual override | must | Changing the OS theme with the app open switches it live | 2 |
| R-29 | Importing from Bitwarden's **unencrypted JSON export** shall be supported, and it shall be the only import path in v1 | must | A fixture export covering **all eight of Bitwarden's item types**, TOTP seeds, folders and custom fields imports with **every** field either mapped or **named in a refusal**, producing the **five of ours they map onto**; nothing is dropped silently. Re-worded by the author as **D-64** rather than quietly weakened, and the correction cuts both ways: it also names *eight* of Bitwarden's types rather than the four everyone quotes, which is what found the fixture covering six | 3 |
| R-30 | Every reachable surface shall be operable by keyboard alone | must | S-08 passes | 3 |

## Interface contract

The boundary is not hardware ↔ software but **`trustvault-core` (plaintext) ↔ webview (untrusted)**,
because the prior-art survey established that the webview's heap cannot be wiped
(`tauri-apps/tauri` discussion #10852). The contract is therefore a security boundary:

- The core owns every plaintext byte. It exposes Tauri commands, never raw state.
- No command returns more than **one** secret value per invocation (R-10).
- Item lists cross the boundary with secrets **elided** — masked placeholders and metadata only.
- `reveal_field(item_id, field_id)` returns one value and starts a 10 s server-side timer; when it
  expires the core pushes a `field-remasked` event and the frontend drops its copy.
- `copy_field(item_id, field_id)` never returns the value at all — the core writes it to the
  clipboard itself and schedules the clear. The secret does not enter JS.
- On lock, the core zeroizes and emits `vault-locked`; the frontend clears its stores on receipt but
  is **not trusted** to have done so — every subsequent command re-checks the lock state.
- Behaviour when the link drops: the webview crashing or reloading does not unlock anything. The
  core's lock state is authoritative and survives a frontend reload.
- Behaviour on power loss mid-write: R-05 atomic save. The previous vault is always the fallback.

## Open questions

- [x] **Import from other password managers** — **closed 2026-08-05, D-42.** One format:
      Bitwarden's unencrypted JSON export. It is the only candidate that carries TOTP seeds,
      folders, custom fields and item types in a documented, stable schema while needing nothing
      but `serde_json` — no XML, no zip, no second crypto stack inside a Tier-1 crate. CSV, KDBX,
      1pux and every vendor's *encrypted* export are out of scope, each with its reason in
      `trustvault-project.md`. R-29 is now testable and carries Phase 3 tasks.
- [x] **Audit log retention** — **closed 2026-08-04, D-31.** The log is a new `audit` key inside the
      sealed body, which §9 of `docs/vault-format.md` already permits without a `format_version`
      bump. Entries buffer in core memory and flush on save, not on every reveal, so reading a
      password does not rewrite the vault file. Capped at 1000 entries, pruned oldest-first. The
      setting is **off by default**, which narrows `MASTER.md` § *Reveal* from an unconditional
      statement to a conditional one — the Settings copy must not imply the log is running when it
      is not.
- [x] **Argon2id default parameters** — **closed 2026-08-02.** Measured, not guessed: 256 MiB / t=3 /
      p=1 gives 511 ms on the dev machine. The per-platform half of the question is answered by
      *not* fixing a per-platform constant — `KdfParams::calibrate` measures the machine at vault
      creation and stores what it found in the header, so the constant is only a starting point.
      Full measurement table and the calibration algorithm: `docs/vault-format.md` §3.2.
